# 1. First, forget Next.js for a minute

Imagine your current React + Parcel application.

You have:

```text
React + TypeScript
       ↓
      Parcel
       ↓
JavaScript bundle
       ↓
Browser
       ↓
React runs
       ↓
UI appears
```

Suppose you have:

```tsx
function App() {
  return <h1>Hello Gopi</h1>;
}
```

Parcel bundles your application.

The browser downloads that JavaScript.

Then React runs:

```text
App()
 ↓
<h1>Hello Gopi</h1>
 ↓
DOM
```

So your browser is doing a **lot of the work**.

---

# 2. Now enter Next.js

Next.js changes the picture.

Imagine you visit:

```text
https://myapp.com/analyzer
```

The browser sends a request:

```text
Browser
   │
   │ GET /analyzer
   ↓
Next.js server
```

Now something interesting happens.

Next.js looks at your application:

```text
app/
└── analyzer/
    └── page.tsx
```

and knows:

> `/analyzer` → `app/analyzer/page.tsx`

It renders the appropriate React tree on the server where applicable, produces the data needed for the client, and sends the result back.

Conceptually:

```text
Browser
   │
   │ GET /analyzer
   ↓
Next.js
   │
   ↓
page.tsx
   │
   ↓
React rendering
   │
   ↓
HTML + React data
   │
   ↓
Browser
```

That's your **first major mental shift**.

---

# 3. So is Next.js a backend?

This is where beginners get confused.

The answer is:

### Kind of—but don't think of it as simply "React + backend."

Next.js is a **full-stack React framework**.

You can have code running on:

```text
                 Next.js
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       SERVER              BROWSER
          │                   │
     API calls             UI
     secrets              events
     databases             state
     server logic
```

That means one project can contain both.

---

# 4. Here's the important part

In your current React application, if you write:

```tsx
console.log("Hello");
```

you generally expect:

```text
Browser console
```

because React is running in the browser.

But in a Next.js **Server Component**, that same:

```tsx
console.log("Hello");
```

may appear in:

```text
Terminal / server logs
```

instead.

🤯

This is one of the first things that feels weird when moving from React SPA → Next.js.

---

# 5. Let's create your first tiny Next.js example

Imagine:

```text
app/
└── page.tsx
```

Inside:

```tsx
export default function Home() {
  console.log("Where am I?");
  
  return <h1>Hello Gopi</h1>;
}
```

Notice something important:

We didn't write:

```tsx
"use client";
```

Therefore, in the App Router, this is a **Server Component by default**.

So:

```text
Request
   ↓
Next.js server
   ↓
Home()
   ↓
console.log()
   ↓
HTML/result sent toward browser
```

The browser doesn't simply receive your original component and execute it like a normal client-side React SPA.

---

# 6. But wait... how can React work in the browser?

Excellent question.

Because Next.js can send the browser what it needs to display the UI, and **Client Components** can be sent as client-side JavaScript when interactivity is required.

Think of two kinds of React components:

### 🖥️ Server Component

```tsx
export default function Page() {
  return <h1>Hello</h1>;
}
```

Good for:

* fetching data
* accessing server resources
* keeping secrets server-side
* generating UI
* reducing client JavaScript

### 🌐 Client Component

```tsx
"use client";

import { useState } from "react";

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}
```

Good for:

* `useState`
* `useEffect`
* click handlers
* browser APIs
* interactive UI

---

# 7. Why does `"use client"` exist?

Let's say your analyzer has this:

```text
Enter URL:
[ https://example.com        ]

[ Analyze ]
```

The input needs browser interaction.

For example:

```tsx
const [url, setUrl] = useState("");
```

The server can't maintain that browser interaction.

So we say:

```tsx
"use client";
```

Now Next understands:

> "This component needs to participate in the client-side React application."

So:

```text
Server
  │
  │ renders surrounding application
  ↓
Client Component
  │
  ↓
Browser JavaScript
  │
  ↓
useState()
onChange()
onClick()
```

# 8. Your analyzer will probably have BOTH

This is where Next.js becomes really useful for your project.

Imagine:

```text
Analyzer Page
│
├── Header
│
├── AnalyzerForm       ← Client
│
├── Results             ← Server/Client depending on design
│
├── PerformanceScore
│
├── Opportunities
│
└── AIRecommendations
```

The form might need:

```tsx
"use client";
```

while other components might not.

So you don't need to turn the **entire application** into client-side React.

That's important.

# 9. The old React mental model

Your current application probably feels like:

```text
Everything
   ↓
Browser
   ↓
React
   ↓
UI
```

Next encourages:

```text
                  Application
                       │
              ┌────────┴────────┐
              ↓                 ↓
           Server             Client
              │                 │
       data + secrets      interaction
       API calls           state
       rendering           events
```

This is probably the **single most important conceptual difference** you'll learn.

Suppose the user enters:

```text

```

and clicks:

```text

```

You want to call Google's performance API.

You *could* theoretically have:

```text
Browser
   ↓

```

```text

   ↓
```

```text
              Browser
                 │
                 │ URL
                 ↓
        ┌─────────────────┐
        │    Next.js      │

        │  Server logic   │
        └────────┬────────┘
                 │
                 ↓
            Google API
```

# 12. Now let's talk about HTML

This is another crucial concept.

Suppose you have:

```tsx
export default function Page() {
  return (
    <main>
      <h1>Web Performance Analyzer</h1>
      <p>Analyze your website.</p>
    </main>
  );
}
```

The user ultimately needs something like:

```html
<main>
  <h1>Web Performance Analyzer</h1>
  <p>Analyze your website.</p>
</main>
```

The difference is **where and when that output is produced**.

In a traditional SPA:

```text
Browser
 ↓
Download JS
 ↓
React executes
 ↓
UI generated
```

With server rendering:

```text
Request
 ↓
Server executes rendering work
 ↓
HTML can be produced
 ↓
Browser receives it
 ↓
Browser displays it
```

# 13. But HTML isn't the whole story

Here's where **hydration** comes in.

Imagine the browser receives:

```html
<button>Analyze</button>
```

The browser can display that.

But how does it know:

```tsx
onClick={handleAnalyze}
```

?

It doesn't.

That's where React's client-side machinery comes in.

Conceptually:

```text
SERVER
   │
   │ HTML
   ↓
BROWSER
   │
   │ display HTML
   ↓
React client code
   │
   ↓
Hydration
   │
   ↓
Interactive UI
```

---

# 14. Hydration in plain English

**Hydration = React attaching/activating client-side behavior onto server-rendered UI.**

So:

```text
HTML
```

is the structure.

Then React makes the relevant parts:

```text
interactive
```

This is why you may hear:

> "Next.js server renders the page and React hydrates it."

That's the basic idea.

# 16. A very important misconception

Don't think:

> "Server Components mean the browser has no React."

No.

Instead:

```text
Server Components
        ↓
Server-side rendering/data work

Client Components
        ↓
Browser-side React behavior
```

A Next.js application can contain both.

---

# 17. One more important rule

You can have:

```text
Server Component
      ↓
Client Component
```

For example:

```tsx
// page.tsx

export default function Page() {
  return (
    <>
      <h1>Analyzer</h1>
      <AnalyzerForm />
    </>
  );
}
```

where:

```tsx
"use client";

export function AnalyzerForm() {
  // state
  // events
}
```

This is perfectly normal.

But the reverse relationship has restrictions: once you're inside a client component tree, you can't casually import a Server Component into it and expect it to magically execute on the server in the same way.

The exact composition rules are worth learning later.

# 18. Let's connect this to your current React knowledge

You already know:

```tsx
function Component() {
  const [state, setState] = useState();

  return ...
}
```

Don't throw that knowledge away.

Instead, add one question:

> **Where does this component execute?**

Every time you write Next.js code, ask:

### Question 1

```text
Server or browser?
```

### Question 2

```text
Does it need state/events/browser APIs?
```

### Question 3

```text
Does it need secrets/server resources?
```

### Question 4

```text
Does it need to be sent to the browser?
```

Those four questions will save you SO many headaches.
